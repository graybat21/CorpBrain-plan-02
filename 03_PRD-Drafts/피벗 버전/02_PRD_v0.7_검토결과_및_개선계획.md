# PRD v0.7 검토 결과 및 개선 계획

**작성자:** AI 동료 다온
**목적:** 기존 PRD v0.7이 "AI가 오해 없이 코드를 생성할 수 있는가", "해석이나 추측 없이 명확한가(I-P-O)"의 관점에서 부족한 점을 짚어내고, 이를 순차적으로 개선하기 위한 계획을 수립합니다.

---

## 1. 주요 검토 결과 (발견된 문제점)

요청하신 "명확성, 테스트 가능성, I-P-O 관점의 데이터 흐름, 시스템 제약 인지" 기준에 따라 검토한 결과, AI(개발자)가 코드를 짜기 위해 **'스스로 추측해서 결정해야 하는 공백'**이 다수 발견되었습니다.

### 📌 A. "테스트 가능한 명확성" 및 "임계치" 부족 (개발자의 추측 유발)
1. **마스킹 범위의 모호함 (1.2, F2):**
   - "완벽한 마스킹 제공", "PII 데이터는 `***`로 마스킹"이라고 되어 있으나, **어떤 데이터를 PII로 볼 것인가**(주민번호, 이메일, 전화번호 등 정규식 기반인지, 사내 기밀 키워드 사전 기반인지)가 없습니다. 기준이 없으면 테스트도 불가능합니다.
2. **Naming Rule의 불확실성 (1.2, F4):**
   - "일관된 Naming Rule 자동 일괄 개편"이라고만 작성되어 있습니다. AI가 추천하는 이름의 포맷(예: `[YYYY-MM-DD]_프로젝트명_분류.docx`)이나, 사용자가 프롬프트를 튜닝할 수 있는지 명세가 필요합니다.
3. **불명확함의 임계치 부재 (F3):**
   - "파일명이 불명확할 경우 첫 1~2문단만 가볍게 읽어와 보완"에서 **'불명확하다'는 조건이 코드로 어떻게 표현되는가?** (예: 파일명 길이가 5자 미만, 특수문자로만 구성된 경우 등)
4. **진행률(Progress) 측정 기준 (F3):**
   - 진행률 측정 시 기준 모수(Denominator)가 '파일 개수'인지 '파일의 전체 바이트 용량'인지 명시해야 합니다.

### 📌 B. 시스템 제약 및 예외 케이스(Edge Case) 방어 누락
1. **Windows 파일 시스템 제약 (F1, F4):**
   - 윈도우 OS의 최대 경로 길이 제한(MAX_PATH, 260자)을 넘는 파일이나 폴더에 접근하거나 Rename할 때의 예외 처리(에러 반환 혹은 스킵)가 없습니다.
   - 접근 권한 거부(Permission Denied) 폴더에 대한 처리 로직이 없습니다.
2. **외부 종속성 오류 (F2):**
   - 로컬 LLM(Ollama)이 사용자의 PC에 설치되어 있지 않거나 실행 중이 아닐 때 앱이 어떻게 반응해야 하는가? (안내 팝업 띄우기 및 다운로드 링크 제공 등)
3. **앱 내부 뷰어의 오버스펙 위험 (F5):**
   - "앱 내부 뷰어 연결"은 MVP 수준에서 .docx나 .pdf 렌더러를 탑재해야 한다는 뜻이 되어 개발 범위가 기하급수적으로 늘어납니다. OS 기본 연결 프로그램으로 열기(`os.startfile`)로 확정해야 합니다.

### 📌 C. Input - Process - Output (데이터 흐름) 연결 끊김
1. **실행 취소(Undo)의 데이터 관측성 (F4):**
   - "100% 원복되어야 한다"를 구현하려면 OS에서 Rename을 수행하기 전에 **원본 경로와 새 경로의 매핑 테이블**이 어딘가(SQLite 등)에 반드시 저장되어야 합니다. 이 데이터 흐름에 대한 명세가 누락되어 있습니다.
2. **분석 옵션의 Output 스펙 (F3):**
   - 옵션 1(고속 분석)과 옵션 2(심층 위키)의 최종 Output 형태가 마크다운(Markdown)인지, JSON인지 등 출력 데이터의 포맷이 명확하지 않습니다.

## 2. 순차적 개선 계획 (Action Plan)

현재 PRD를 한 번에 전부 뜯어고치기보다, **가장 뼈대가 되는 데이터 흐름부터 예외 처리까지 3단계에 걸쳐 고도화**하는 것을 제안합니다.

### 🟢 [Phase 1] Input-Process-Output 및 임계치 명확화
- **목표:** 개발자가 "이게 무슨 뜻이지?" 하고 추측하지 않도록 수치와 포맷을 못 박습니다.
- **작업 내용:**
  1. PII 마스킹 대상 정규식/패턴 명확화
  2. "불명확한 파일명"의 프로그래밍적 조건(길이, 키워드) 정의
  3. AI 추천 파일명(Naming Rule)의 기본 템플릿 구조 정의
  4. 옵션 1과 옵션 2의 명확한 Output 스펙 정의

### 🟡 [Phase 2] 시스템 제약 및 예외 케이스(Edge Case) 추가
- **목표:** 무한루프, 크래시(Crash), 리소스 낭비를 막기 위한 물리적 방어선을 구축합니다.
- **작업 내용:**
  1. 윈도우 OS 경로 260자 제한 및 권한 거부(Access Denied) 시 스킵 로직 추가
  2. Ollama 프로세스 미동작 시 fallback UI 설계
  3. 대량 파일(10만 개 이상) 스캔 시 UI Freezing 방지를 위한 청크 스캔 제약

### 🔴 [Phase 3] 내부 구조 및 DB 스키마 추적성 확보 (Observability)
- **목표:** '실행 취소'나 '캐시 재사용' 등 상태를 유지해야 하는 기능들의 데이터 흐름을 구체화합니다.
- **작업 내용:**
  1. SQLite에 저장될 `File_Meta` 테이블 및 `Rename_History` 테이블의 핵심 컬럼 정의
  2. 파일 변경 감지(캐싱)를 위한 Hash(예: MD5/SHA256) 혹은 수정 시간(mtime) 활용 기준 명시
  3. 딥링크(`os.startfile`) 실행을 위한 프로세스 흐름 정의
